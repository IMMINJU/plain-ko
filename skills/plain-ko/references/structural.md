# 구조 규칙

어휘 사전으로는 안 잡히는 것들. 앞쪽(S1–S6, S14)은 `scan.mjs`가 결정적으로 센다.
뒤쪽(S7–S12)은 세는 게 불가능해서 판정 단계로 넘긴다.

임계값은 관측치다. 절대 기준이 아니라 "이 정도면 눈에 띈다"는 선이고,
자기 글로 다시 재서 조정하는 게 맞다.

예시는 전부 패턴을 보여주려고 지어낸 문장이다.

---

## 결정적으로 세는 것

### S1. 부정 대구 — `X가 아니라 Y다`

단일 패턴으로 발화량이 가장 많다.

**한 가지 형태만 보면 절반을 놓친다.** 아래는 모두 같은 구조다.

```
문제는 처리량이 아니라 지연이었다
큐를 늘린 게 아니라, 재시도 조건을 좁힌 거다
해결책이 아닌 임시방편
설정을 바꾼 것이지, 코드를 고친 게 아니었다
```

영어 `It's not just X, it's Y` 의 대응이지만 한국어에서는 정당한 용법의 비중이 더 크다.
그래서 **개수를 세되 자동으로 죽이지 않는다.**

정당한 경우 — 앞에서 실제로 그렇게 믿었고, 그게 틀렸다는 걸 지금 뒤집는 것:

```
느린 건 DB 조회가 아니라 그 앞의 직렬화였다
```
앞 문단에 "DB 조회를 의심했다"가 실제로 적혀 있어야 성립한다. 부정하는 쪽에 내용이 있다.

죽여야 하는 경우 — 아무도 믿은 적 없는 걸 세워놓고 부수는 것:

```
중요한 건 도구가 아니라 도구를 쓰는 순서다
    → 순서가 중요하다
```
"도구가 중요하다"고 주장한 사람이 글 안에 없다. 지우면 문장이 짧아지고 세진다.

**판정 질문**: 부정당하는 쪽이 이 글 안에서 실제로 주장된 적이 있나? 없으면 리듬용이다.

같은 대구가 한 글에서 반복되는 것도 본다. 같은 대비가 세 번 넘게 나오면
새 주장이 아니라 앞 문장의 재진술이다.

### S2. 콜론 제목

```
### 설계: 큐를 하나 더 두는 선택
### 구현: 재시도 조건을 좁히다
### 검증: 부하 테스트 결과
```

콜론 왼쪽이 라벨, 오른쪽이 내용인 구조는 제목이 아니라 **표의 행**이다.
연속된 제목이 전부 같은 꼴이면 목차를 기계가 채운 티가 난다.

교정은 콜론을 지우는 게 아니라 제목을 문장으로 바꾸는 것:

```
## 재시도 로직: 과감한 정리
    → ## 재시도 조건을 두 개로 줄였다
```

예외: 콜론 오른쪽이 고유명사·수치인 경우(`## 결과: 302 → 278`)는 라벨이 맞다.

### S2-c. 서수·순번 제목

```
## 1차 시도
## 두 번째 벽
## 가설 2
```

과정을 그대로 목차로 옮긴 흔적이다. 번호는 순서만 알려주고 내용을 안 알려준다.
그 단계에서 **무엇이 밝혀졌는지**를 제목에 쓴다.

```
## 2차 시도 → ## capability 를 줬는데도 같은 에러가 났다
```

### S2-b / S2-d. 다른 정형 제목

`## 제목 — 부연` 과 `## "그거 왜 안 되죠?"`.

전자는 제목을 두 번 쓰는 구조다. 붙임말을 떼고 한 문장으로 만든다.
후자는 실제 발언을 그대로 올리는 것이라 한 번은 정당한데, 연속되면 장치가 된다.

둘 다 `context` 티어라 기본 실행에서는 뜨지 않는다. `--all` 로 본다.

### S3. 볼드 밀도

강조가 고르게 뿌려지면 강조 기능이 죽는다. 한 문단에 볼드가 둘 이상이면
그 문단은 강조가 없는 것과 같다.

같이 보는 것: `- **용어**: 설명` 꼴의 불릿. 사전 항목이지 문장이 아니다.
리스트 전체가 이 꼴이면 산문으로 풀거나 진짜 표로 바꾼다.

### S15. 리드 볼드 연속 · S16. 긴 볼드

볼드 개수는 밀도로만 보지만, 이 둘은 위치가 특정되므로 항목으로 낸다.

**S15** — 문단 첫머리 볼드가 세 개 이상 이어지는 경우.

```
**첫째, 위기가 누적되고 있었다.** kubectl 단절 위기 2회…
**둘째, 통로가 단일 노드에 묶여 있었다.** 이게 안 풀린 상태에선…
**셋째, 진짜 원인은 인프라 측 변수일 가능성이 크다.** 거기서 더 파면…
```

셋이 다 굵으면 어느 것도 안 굵다. 강조가 아니라 서식 습관이다. 하나만 남긴다.

**S16** — 볼드 안이 40자를 넘는 경우. 그 길이면 강조가 아니라 굵은 본문이다.
강조할 어절만 남기고 나머지는 푼다.

### S3-b. 밀도 지표

개별 히트가 틀린 게 아니라 **밀도가 문제**인 패턴들. 사전에 넣으면 오탐이 쏟아지고,
`context` 로 넣어도 문서마다 수십 건씩 떠서 후보 목록을 못 쓰게 만든다.
그래서 세기만 하고 판정은 안 한다. 1,000자당 비율이다.

| 지표 | 임계 | 무엇을 보나 |
|---|---|---|
| 피동 | 3.0 | `되었` `되는` `된 ` `어졌` `여졌` |
| 가능표현 | 3.0 | `~할 수 있` 류 |
| 에대해 | 1.0 | `에 대해` `에 대한` `에 관해` |
| 의존명사것 | 16.0 | `것이` `것을` `것은` `게` `걸` |
| 복수들 | 5.0 | `~들이` `~들을` 류 |

임계를 넘었다는 건 틀렸다는 뜻이 아니라 **한 번 훑어보라**는 뜻이다.
`의존명사것`은 한국어에서 원래 높아서 임계도 높다. 600자 미만 문서에는 적용하지 않는다.

### S4. 정형 소제목

`돌아보며` · `마치며` · `정리하며` · `배운 것` · `교훈` · `마무리` · `들어가며` · `시작하며`

내용이 없는 제목이다. 그 자리에 결론을 넣는다.

```
## 마치며              → ## 큐를 늘리는 대신 조건을 좁혔다
## 돌아보며: 실패였을까 → ## 실패는 아니었다
```

두 번째 예시는 자문자답까지 같이 죽은 경우다. `~아닌가?` 로 묻고 다음 문단에서
`아니었다`로 답하는 구조는 제목과 본문 양쪽에서 나온다.

### S5. 명사화 종결

`~라는 것이다` · `~인 셈이다` · `~라는 점이다` · `~라는 뜻이다`

동사로 끝낼 자리를 명사로 감싸서 한 겹 멀어지게 한다.

```
순서가 중요하다는 것이다 → 순서가 중요하다
```

예외: 앞 문장을 요약해 다시 정의할 때는 정당하다. 연속 두 문장 이상에서 나오면 습관이다.

### S6. `이다` 회피

`역할을 한다` · `에 해당한다` · `로 작용한다` · `를 의미한다` · `라고 볼 수 있다`

영어 `serves as` / `functions as` 의 대응. 그냥 `~다`로 쓸 자리를 늘린 것이다.

### S13. `있었다` 종결

무슨 일이 일어났는지 대신 **무엇이 있었는지**를 말하는 자리다.

```
로그에 같은 에러가 세 건 있었다   → 같은 에러가 세 번 찍혔다
확인이 필요한 부분이 있었다      → 두 군데를 더 확인해야 했다
```

정당한 경우도 있다. 상태를 진술하는 게 요점일 때다. 한 문단에 두 번 이상이면 본다.

### S14. em dash

`—` 와 `–`. 한국어 문장부호가 아니고, 대개 문장부호 선택을 회피한 자리다.

```
큐를 늘렸다 — 그래도 밀렸다   → 큐를 늘렸다. 그래도 밀렸다
설정 세 줄 — 그게 전부였다    → 설정 세 줄이 전부였다
```

쉼표·괄호로 바꾸거나 문장을 나눈다. 제목보다 본문에서 훨씬 많이 나오므로 둘 다 본다.

## 일부만 세는 것

### S7. 예고와 회수

```
여기에 함정이 있다
이게 뒤에 나올 문제의 예고편이었다
그 얘기는 마지막에 한다
말로는 다 그럴듯하다. 실제로 뭘 잡았는지가 중요하다
```

지금 말할 수 있는 걸 미루면서 긴장을 만드는 척하는 문장. 기술 글에서는 거의 항상
손해다 — 독자는 이미 결론을 보러 왔다.

교정은 삭제하거나, 그 자리에 미루려던 내용을 바로 넣는 것:

```
이게 뒤에 나올 문제의 예고편이었다
    → 같은 원인이 배포 단계에서 한 번 더 터졌다
```

정형구(`함정이 있다`, `예고편`, `뒤에 나올`, `마지막에 한다`, `나중에 다룬다`)는
스캔이 잡는다. 그 밖의 변형은 본문을 읽어야 나온다.

### S8. 3항 나열

할 말이 정확히 셋일 때는 셋이다. 문제는 리듬을 채우려고 셋이 되는 경우다.
둘이면 충분하고 넷이면 대체로 정직한데, 셋이 의심스럽다.

가설이나 원인을 나열할 때 특히 자주 셋이 된다.
`가설 세 개를 세웠다` 뒤에 오는 목록은 한 번 세어볼 만하다.

**판정 질문**: 세 번째 항목을 지우면 뜻이 줄어드나? 안 줄면 리듬용이다.

스캔은 `근거 셋` · `이유 세 가지` 처럼 개수를 예고하는 표현만 잡는다.
예고 없이 그냥 셋을 나열한 경우는 본문을 읽어야 나온다.

## 스캔이 못 보는 것

아래 둘은 문서 전체 구조라 정규식으로 안 잡힌다. **스캔 결과만 보고 끝내지 않는다.**

### S9. 문장 길이 균일

한 문단 안에서 가장 긴 문장과 가장 짧은 문장의 길이 차가 2배 미만이면 본다.

**한국어에서는 약한 신호다.** 영어권에서 말하는 "문장 길이가 균일하다"를
그대로 옮기지 않는다. 리듬이 굳어 보일 때만 참고한다.

### S10. 절마다 교훈으로 닫기

모든 섹션이 `~라는 걸 배웠다` / `~가 더 자주 옳다` / `~해야 한다`로 끝나면 틀이 드러난다.
글 전체에서 하나만 남기고 나머지 절은 사실로 끝낸다.

### S11. 제목 클리셰

`딥다이브` · `해부` · `언더 더 후드` · `완벽 가이드` · `~하는 법` · `왜 중요한가` ·
`모든 것` · `총정리` · `A to Z`

의문형 제목은 넣지 않는다. `## 왜 A는 되고 B는 안 되는가` 같은 제목은
한국어 기술 글에서 흔한 정당한 형식이다.

### S12. 재명명 회피

같은 대상을 반복하기 싫어서 문장마다 다른 이름으로 부르는 것.
`감사 → 검증 → 점검 → 리뷰` 가 한 문단에서 모두 같은 걸 가리키면
독자는 넷을 다른 것으로 읽는다.

사람은 같은 말을 그냥 반복한다. 반복이 거슬리면 대명사를 쓰거나 문장을 합친다.
새 이름을 만들지 않는다.

## 이 도구가 세지 않는 것

맞춤법·띄어쓰기·문장부호 규범은 범위 밖이다. 번역투는 `lexicon.md` 의 L6에서
얕게만 본다 — 문자열로 잡히는 것까지고, 형태소 분석이 필요한 범위는 안 건드린다.
